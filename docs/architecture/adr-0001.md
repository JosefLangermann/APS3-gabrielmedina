# ADR 0001 — Uso de RabbitMQ para processamento assíncrono do match de candidaturas

**Status:** Aprovado (arquitetura proposta)  
**Data:** 2026-11-10

## Contexto

Ao submeter uma candidatura, o aluno precisa ter seus dados validados e registrados. A identificação de vagas compatíveis depende, porém, da consulta ao perfil acadêmico e da execução do algoritmo de compatibilidade. Essas etapas dependem de serviços distintos e podem apresentar latência variável.

Executar todo o processamento dentro da mesma requisição HTTP manteria o aluno aguardando, aumentaria o risco de timeout e criaria dependência temporal entre a API, o serviço de competências e o serviço de match. Também seria mais difícil recuperar o processamento após uma indisponibilidade temporária.

## Decisão

Adotar RabbitMQ com protocolo AMQP 0-9-1 para desacoplar a API de Aplicação dos serviços de competências e de match. A API registra a candidatura com estado `RECEBIDA`, publica uma solicitação de coleta de competências e responde ao cliente com HTTP `202 Accepted` e um `CandidaturaStatusDTO`.

O processamento seguirá esta ordem orientada a eventos:

1. A API valida os dados, persiste a candidatura e publica `SolicitacaoCompetenciasEvento`.
2. O `CompetenciaService` consome a solicitação, consulta o Sistema Acadêmico e publica `CompetenciasDisponiveisEvento`.
3. O `MatchService` consome o evento de competências, consulta as vagas ativas, calcula os scores e publica `ResultadoMatchEvento`.
4. A API consome o resultado e atualiza a candidatura para `PROCESSADA` ou `SEM_MATCH`. Se as tentativas de obtenção de competências ou de match forem esgotadas, registra `FALHA_PROCESSAMENTO`.
5. O aluno consulta o andamento por meio de `GET /candidaturas/{id}`.

Cada evento deve carregar, no mínimo, `eventId`, `candidaturaId`, `alunoId`, `correlationId` e `occurredAt`, além dos dados específicos do evento. Os consumidores devem ser idempotentes para evitar efeitos duplicados em caso de reentrega.

## Consequências

### Vantagens

- **Desacoplamento:** os serviços comunicam-se por contratos de eventos, sem exigir que estejam disponíveis no mesmo instante.
- **Resposta HTTP rápida:** a API confirma o recebimento da candidatura sem aguardar a execução do match.
- **Resiliência:** filas, confirmação de consumo, retentativas e dead-letter queue permitem tratar falhas temporárias.
- **Escalabilidade:** consumidores do serviço de match podem ser replicados conforme o volume de eventos.
- **Rastreabilidade:** identificadores de correlação permitem acompanhar uma candidatura ao longo do pipeline.

### Débitos e riscos aceitos

- **Consistência eventual:** o resultado não estará disponível necessariamente no momento da submissão; o frontend deverá consultar o status periodicamente ou receber uma notificação futura.
- **Complexidade operacional:** RabbitMQ exige monitoramento, configuração de filas, retentativas e dead-letter queues.
- **Duplicidade e reordenação:** mensagens podem ser entregues novamente; consumidores precisam ser idempotentes e validar o estado atual da candidatura.
- **Publicação e persistência:** existe risco de salvar a candidatura e falhar ao publicar o evento. Em uma implementação de produção, recomenda-se o padrão Transactional Outbox para garantir a publicação confiável.
- **Infraestrutura adicional:** o broker aumenta o custo de implantação e manutenção.

Esta ADR descreve a arquitetura proposta para a funcionalidade; a adoção das tecnologias depende da implementação e configuração efetivas do projeto.
